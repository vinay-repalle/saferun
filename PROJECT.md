# SafeRun — Project

Developer tool that checks AI-generated code *before* it is run or trusted. The CLI (`saferun`) is the product; `web/` is a static informational website. One validation engine, one sandbox. SafeRun is **Python-only**.

**Non-goals:** generating/repairing code, multi-agent systems, LLM API calls, any claim that a passing scan means the code is secure (PASS is not proof of safety).

**Where things are:** this file = how SafeRun works now (design, threat model, limits). [STAGES.md](STAGES.md) = rules, status, next steps. [docs/](docs/) = CLI, engine, sandbox, release, benchmark guides. [docs/history.md](docs/history.md) = old status log, test evidence, removed features (archive, not current).

## Architecture
```
saferun/
  sandbox/   workspace copy + locked-down docker run
  engine/    checks -> normalized findings -> verdict
  cli.py     `saferun scan|run|init|status|doctor|verify-images|osv-db|check-names` (docs/cli.md)
web/         React + Vite static website (no scanning, no server)
```
**Sandbox** (`saferun/sandbox/`): `workspace.py` (sanitized temp copy) · `docker.py` (defensive CLI wrappers, daemon preflight) · `copy.py` (fd-relative, identity-verified, limited copy) · `secrets.py` (credential signatures, output redaction) · `reaper.py` (orphan recovery) · `controls.py` (what is really in force; pure functions) · `runner.py` (`build_create_args` holds every security flag; `run_sandboxed` = preflight → create → **verify applied config, fail closed** → start → timeout → inspect → cleanup) · `attestation.py` (kernel-view probe) · `profiles.py` (python image) · `config.py` (limits/result types) · `images.py`, `verify.py`, `analyzer.py`, `signature.py` (pins, verification, cosign). Uses the docker CLI via argument lists (no shell, no Docker SDK, no socket handed to anything untrusted). No backend interface: not needed with a single backend (the seams are `build_create_args`, `controls.py`, `SandboxResult`).

## Validation engine (Phase 2, `saferun/engine/`)
`model.py` (Finding, CheckResult, CheckStatus, Severity, ValidationReport) · `verdict.py` · `tools.py` (controlled subprocess runner) · one module per check, each `run_check(ctx) -> CheckResult`: `semgrep.py`, `osv.py`, `secretscan.py`, `pysyntax.py` · `engine.py` (`validate_project`) · `context.py` (injectable runners for tests) · `paths.py` · `explain.py` · `accept.py` · `osvdb.py` · `analyzer.py` · `rules/python.yml` (bundled Semgrep rules) · `rules/gitleaks.toml`.

Flow: `create_workspace` (sanitized copy) → list files → run enabled checks (each guarded: an exception becomes an `error` result) → `compute_verdict` → delete the copy.

**Where each tool runs.** Everything that parses untrusted files runs **inside a container**: the Python syntax check (`compile()`) in the `python` image; Semgrep, OSV-Scanner and gitleaks in the **analyzer image**. All use the same `run_sandboxed` path with the same verified restrictions (no network, read-only root and project, non-root, all capabilities dropped, seccomp/no-new-privileges, memory/swap/CPU/pids/fd/file-size limits, container-side kill deadline). Only OSV-Scanner gets one extra mount: the offline OSV data directory, read-only (the applied mount set is verified exactly). Semgrep uses the rule file baked into the image (a project cannot supply rules) and `--disable-nosem`. The host never executes Semgrep, OSV-Scanner or gitleaks, and the host environment is not passed in. **No host fallback.** The tools only read project code; none executes it.

**Dependency handling.** SafeRun never installs, fetches or builds dependencies and never runs install scripts. OSV-Scanner reads dependency files only (`--no-resolve`): lockfiles (`poetry.lock`, `Pipfile.lock`, `pdm.lock`, `uv.lock`) and the manifest `requirements.txt`. Scans use no network: OSV-Scanner runs offline against local OSV data (`saferun osv-db update` is the only download, of public data; nothing about any project is sent); without the data the check reports `error`. A manifest without a scannable file beside it (`Pipfile`, `pyproject.toml`) and requirements variants (`requirements-dev.txt`, …) are *coverage gaps*: `incomplete`/`skipped`, never clean. `requirements.txt` entries not pinned with `==` are noted as not reliably matched (evaluated at their lower bound; no transitive resolution).

**Findings vs operational errors.** A finding is a signal in the project. `error`/`timeout`/`unavailable`/`skipped`/`incomplete` describe the analysis, carry no findings (except `incomplete`, which keeps partial results) and force at least `WARNING`; operational failures are never FAIL. Severity: Semgrep → rule's `saferun_severity` else ERROR/WARNING/INFO → high/medium/low; OSV → CVSS of the vulnerability group (≥9 critical, ≥7 high, ≥4 medium, >0 low) else the database label, else `unknown` (treated as medium); Python syntax error → medium (a validation problem, not a demonstrated vulnerability); gitleaks secret → high (value never kept); withheld private key/token → high, withheld private-mode file → low. `PASS` needs at least one completed analysis check and no partial scan; a non-empty `skipped`/`withheld` workspace is a partial scan (WARNING at least). Verdict rules: [docs/engine.md](docs/engine.md) / `verdict.py`. Tool-derived strings are stripped of control and bidi characters and length-bounded; tool-reported paths are accepted only as relative paths inside the copy.

**Limitations.** Semgrep rules are a small starting set (14 rules, Python only), no taint or cross-file analysis; Python syntax is checked with the sandbox image's Python 3.12 only (Semgrep tolerates syntax errors and does not report them); OSV matches known vulnerabilities only (no malware detection, no reachability; look-alike names are a separate offline hint, `saferun check-names`, not part of `scan`); unsupported file formats are not scanned; Semgrep skips files > 1 MB (reported `incomplete`); at most 50 lockfiles and 1000 findings per check; rule quality is measured only by a small advisory benchmark of simulated samples ([docs/benchmark.md](docs/benchmark.md)), not independently evaluated; verdict thresholds are policy choices, not validated.

## Threat model
**Assets:** host files/credentials, Docker daemon, host CPU/RAM/disk, network position, other scans' data. **Attacker:** author of the scanned project (or an LLM that wrote it): malicious code, tests, archives, filenames, dependency manifests; also hostile output (size, terminal escapes).

| Threat | Control |
|---|---|
| Read/modify host files; credential exposure | Only a sanitized *copy* is mounted, read-only; symlinks/special files not copied; concurrent modification *detected* (not prevented, no atomic snapshot); size/count/depth limits; no other mounts |
| Docker socket / credentials | Never mounted; env passed explicitly (none inherited) |
| Docker applying something weaker than asked | After `docker create`, before `start`, 28 properties are checked from `docker inspect`; any deviation raises and the code never runs |
| Daemon unable to enforce a control | Preflight refuses unless the caller lists the control in `allow_degraded`; every control's state is returned in `SandboxResult.controls` |
| Wrong/swapped image; implicit pull; option injection | `--pull never`; created from the resolved image ID (`image_id`); validated image reference; `--entrypoint ""`; argv list, never shell; images declaring `VOLUME` refused |
| Remote/odd Docker endpoint | Only `unix://` accepted (from `DOCKER_HOST` or current context) |
| Privilege escalation | uid 65534, `--cap-drop ALL`, `no-new-privileges`, not privileged, daemon-default seccomp + AppArmor (checked) |
| Persistence/tampering | `--read-only` rootfs; `/tmp` tmpfs `noexec,nosuid,nodev`, size-capped; `/dev/shm` size-capped |
| Network exfiltration / SSRF | `--network none` |
| CPU/memory/fork bomb/disk | `--cpus`, `--memory`=`--memory-swap`, `--pids-limit`, `ulimit nofile/fsize/core`, tmpfs and shm size |
| Hang | Host-side timeout → `docker kill`; container-side `timeout -s KILL`; container always `rm -f`'d |
| Output flooding | Output capped (256 KiB default), excess drained; log driver `none` |
| Leftovers | Container removal verified and workspace deleted independently in `finally`; `reap_orphans()` for crashes |

**Evidence** (automated tests on this host, Docker 29.8.0, kernel 7.0, AppArmor `docker-default`; each control also shown to fail when disabled): seccomp active (`Seccomp: 2`); AppArmor enforce when the daemon reports it; `memory.swap.max == 0`, `memory.max`, `pids.max`; copy limits (400 MiB / 20 000 files / depth 32) checked before and during the copy; identity-verified copy with a final validation pass (`test_races.py`); container-side kill of a run whose parent was SIGKILLed; `reap_orphans()` removes only SafeRun-labelled containers past their deadline and flock-free `saferun-ws-*` dirs; withheld sensitive files and hard links (`test_sensitive.py`, `test_hardlinks.py`); applied-config verification, 28 checks, fail closed (`test_hardening.py`); daemon preflight; kernel-view `attest(image)`; robustness to malformed Docker output, daemon down, hung CLI, kill that does not stop the container; 6 concurrent runs isolated and cleaned up; both cleanup steps always run. Behavioural evidence: no network/DNS, read-only fs except `/tmp`, `/tmp` noexec, OOM kill, exact PID limit, file-size ulimit, output cap. The seccomp filter and AppArmor profile come from the daemon defaults and are checked, not audited or pinned.

## Operational assumptions and known exposures (read before relying on SafeRun)
- **`docker` binary, `PATH` and the local daemon are trusted.** `docker` is resolved from `PATH` to an absolute path and honours `DOCKER_CONFIG`/`DOCKER_CONTEXT`; whoever controls those controls the sandbox. Remote endpoints are refused. Checked with the default context only; rootless Docker and Podman are untested.
- **Docker group = root;** no userns remap (container uid 65534 is host uid 65534).
- **Shared kernel.** Container escapes via kernel/runc bugs are not mitigated or assessed; not proven secure; gVisor/Kata are deferred.
- **`/proc` and `/sys` expose host information** to scanned code (kernel version, CPU model, memory size, and `/proc/self/mountinfo` reveals the host workspace path and overlay layer paths).
- **File permissions are rewritten** in the copy: files 0644, dirs 0755, executable bits dropped. Files not world-readable in the source are withheld rather than widened; `SensitivePolicy(honor_private_modes=False)` opts out.
- **Sensitive files.** Withheld (not copied, listed in `SandboxResult.withheld`): non-world-readable files/directories, and files whose *content* carries a credential signature (PEM private key with body; AWS, GitHub, Slack, Google, Stripe-live, PyPI, Anthropic token formats), by content/mode never by filename; `SensitivePolicy.allow_paths` opts single paths back in. A world-readable file with a secret in an unrecognised format **is** visible to sandboxed code. Output is redacted best-effort (code can encode a secret first). Withheld files are *not analysed*; any non-empty `withheld`/`skipped` means a partial scan and is reported as such. Secret values live in host memory during a run.
- **Concurrent modification of the source tree.** SafeRun copies a *live* directory; there is no atomic snapshot (that needs LVM/btrfs/ZFS/overlay). A pre-scan records a signature (type/mode, dev, ino, size, mtime_ns, ctime_ns) of every entry and each directory's names; the copy requires lstat and the opened fd to match, listings to match and files unchanged after reading; a final pass re-validates every directory and entry. Any difference aborts with `WorkspaceChangedError` (retry); nothing is kept. Not detected: changes after the final validation (they cannot alter copied files), changes leaving every recorded field identical (possible within one timestamp tick on kernels < 6.13 or coarse-timestamp filesystems; untested there), content present at scan time, cross-file inconsistency that predates the scan. A concurrent writer can force repeated aborts.
- **Hard links.** A multi-link file is copied only if every name of its inode was seen inside the scanned tree; otherwise skipped as `hardlink-external` (stops a link to e.g. `~/.ssh/id_rsa`). Relies on `st_nlink` (verified on ext4 only); snapshot trees (`cp -al`) are skipped.
- **Symlinks, FIFOs, devices are not copied** and are listed in `SandboxResult.skipped` (untrusted names; sanitize before display). Bind mounts/submounts inside the project are not detected.
- **`/dev/shm`** is size-capped (`shm_mb`, default 16), verified, and charged to the memory cgroup.
- **Infrastructure errors vs program errors.** Failures before the code starts (preflight, validation, `create`, config verification) and an unreadable final state raise `SandboxError`. Once started, Docker/`timeout` failures look like a normal result: exit 125/126/127 (also used by programs) and Docker's text in `stderr`, which a program can imitate. Exit 137 = SIGKILL (OOM or timeout; use `oom_killed` / `timed_out`). Treat stderr as untrusted. Images must provide `timeout` and `sh` (verified on the two Debian-slim images only).
- **Timeouts:** host-side limit is wall-clock from `docker start` (create time excluded); container-side limit is `timeout_s + container_grace_s`. Both best-effort against a hung daemon.
- **Orphan recovery is explicit:** `reap_orphans()` is not called automatically by the CLI. Containers use `saferun-` names and a `saferun.deadline` label; workspaces live in the system temp dir.
- Images are referenced by pinned digest but each run uses the *resolved image ID*. Sandbox output is not terminal-escape sanitized by the sandbox; the CLI strips control/escape characters from everything it prints.
- **Not covered:** side channels; running scanners on hostile input outside the container (impossible now); dependency installation (never done).
- **Untested for real:** a truly hung `dockerd`, a full disk, rootless Docker, Podman, a host without AppArmor or with seccomp disabled (those paths are unit-tested with fakes), non-default or remote contexts (remote refusal exercised via `DOCKER_HOST` only), kernels < 6.13, a real second OS user (simulated by changing the uid SafeRun sees), CPU throttling accuracy (only the quota is checked). Redaction of analyzer output is untested.

## Runtime profiles and removed features
A *profile* (`profiles.py`) names an image plus its interpreter; every profile gets the same restrictions, verified the same way. There is one: **python** → `python:3.12-slim@sha256:78387bc3…` (pinned by digest, pulled by `saferun init`; the tag has since moved, the pin stays on the tested digest; changing a pin is a deliberate reviewed change: re-run the suite and `verify-images`).

**JavaScript was removed** (Stage 13). The Node image, `javascript-syntax` check, npm OSV data and npm lockfile scan are gone. `--no-javascript-check` is still accepted (hidden, no-op). A project with `package.json`, `package-lock.json`, `yarn.lock` or `pnpm-lock.yaml` (outside `node_modules`) gets the dependency-check note "JavaScript/npm dependencies are not supported and were not scanned." (no effect on status or verdict; with only npm files the check is `not_applicable`, never a pass). The secrets scan still reads files of any type. The website is built with Node but is not part of the scanner.

**The web dashboard and API were removed** (Phase 4: `saferun/api`, `saferun-web`, ZIP upload, loopback guard). SafeRun has no network-facing component: the CLI is the only way to scan.

## Image pinning
Profiles and `DEFAULT_IMAGE` use `repo:tag@sha256:<index digest>` from `saferun/sandbox/images.py`; Docker resolves by digest, the tag is only a label. `dk.resolve_image` (every `preflight`) also checks the local image's `RepoDigests` contain the pin and raises `SandboxError` otherwise, before any container exists. The `tool` string of `python-syntax` is unchanged (`RuntimeProfile.label`); error text quoting an image shows the full `repo:tag@sha256:` reference. `docker/analyzer/` holds the analyzer build recipe (base by digest, hash-locked Semgrep wheels, SHA-256-verified OSV-Scanner and gitleaks).

## Phase 5 security status (5B isolation, 5C adversarial testing)
**Protected by design.** Hostile source and dependency files are parsed only inside a container with: no network (verified from `docker inspect` before start), read-only root, the project mounted read-only (a sanitized copy), a read-only OSV data mount, uid 65534, `--cap-drop ALL`, `no-new-privileges`, the daemon's seccomp profile, memory = swap limit, CPU and pids limits, fd and file-size ulimits, a private noexec tmpfs, no ports/devices, log driver off, `--init`, container-side `timeout -s KILL` plus host-side kill. The image is built from a digest-pinned base, hash-locked Semgrep wheels and checksum-verified OSV-Scanner and gitleaks binaries; before **every** use SafeRun checks the image ID against the build lock and the tool-version and rules-hash labels against its own pins, then runs the container *by that ID*. Image missing / ID or label mismatch / Docker unusable / policy violated → the check is `unavailable` or `error` (never clean, verdict at best WARNING). No host-side execution path: asserted statically (AST test: no `run_tool`/`find_tool`/`subprocess`/`which` in the check modules), dynamically (`subprocess.Popen`/`run` patched to raise during a scan with the analyzer unavailable; `os.system` and the `exec*` family are NOT covered), and end to end (host `semgrep`/`osv-scanner` shims on PATH are never started).

**Network.** Scans are always offline. `saferun osv-db update` is the only normal download (public OSV data over HTTPS; size cap; the server's MD5 header is REQUIRED; a readable zip with at least a floor of advisories (PyPI 5 000); SHA-256/size/entry count/time in `manifest.json`; atomic replace; existing directories never chmod'ed; symlinked directories refused; `--allow-unverified` records `unverified`). The opt-in `saferun check-names --online` also contacts pypi.org (names only). Per-scan online OSV queries were removed on purpose: network in the analyzer container would expose the host bridge/LAN to a process parsing hostile input, and Docker alone cannot restrict egress to api.osv.dev. Consequence: lockfiles without local OSV data give WARNING (error). Data freshness is the operator's job.

**Tested controls vs proven guarantees.** The adversarial suite (5C) tried hostile inputs on this host and each ended safely: deeply nested/oversized/NUL/non-UTF-8 sources; malformed, nested and huge lockfiles; requirements directives pointing at host files and metadata endpoints; symlinks, FIFOs, sockets, external hardlinks; fork bomb, OOM, CPU spin, tmpfs/output flood, fd exhaustion; mount/unshare/chroot/proc-write/cgroup-write attempts; DNS and TCP attempts; tampered lock, crashing analyzer, missing data; CLI exit codes and report schema. **A passing test is evidence for that input on that host, not a proof.** Not established: absence of Semgrep/OSV-Scanner/gitleaks/Go/Python parser vulnerabilities, kernel or runc escapes, behaviour on other kernels/Docker versions/rootless/userns remapping, other CPU architectures (analyzer lock is linux/amd64), SELinux, side channels, the contents of the AppArmor profile.

**Remaining limitations.**
- **Analyzer image trust.** Pinned by a local lock file (image ID, written by `build.sh` or `init`). The lock is trusted only if it and its directory are owned by the current user and owner-only (0600/0700), opened without following symlinks; anything else fails closed *before* Docker is consulted. This stops accidental or group/other tampering, **not** the same user, root, or any `docker`-group member replacing the image and rewriting the lock. Labels (tool versions, rules hash) are set by whoever builds an image and prove nothing alone; the ID in the lock is the control. `build.sh` locks whatever it just built without review. Only the immediate lock directory is examined. A published, cosign-signed image whose digest is pinned in `ANALYZER_RELEASE` is installed by `init` by default; `--build-local` builds locally. After installation the local lock remains the anchor. Cosign runs on the host and parses registry/Sigstore data; the analyzer cannot be installed on a machine that never has internet; account/repository takeover would allow validly signed malicious tags; cosign output format differences between versions are not covered (only `critical.image` / `critical.identity` are read).
- **OSV data trust.** Re-validated before every scan against `manifest.json` (SHA-256, size, floor, symlinks/readability, timestamps); invalid → `error`, older than 30 days → `incomplete`, neither ever clean. The MD5 comes from the same server over the same TLS connection (detects corruption, not a compromised server); SHA-256 is computed locally after download (detects later modification, does not authenticate the download); the manifest sits next to the data; OSV publishes no signature SafeRun checks; the floors are sanity checks; a file swapped between validation and the container's read is not detected. Freshness is reported in each dependency check's notes and by `saferun osv-db status`.
- The OSV-Scanner and gitleaks checksums come from the same upstream release as the binary (integrity, not authenticity); Semgrep wheel hashes were generated from PyPI at lock time (Linux x86_64, CPython 3.12 only).
- Coverage cross-check quirk: files whose names contain control characters are reported with sanitized paths, so Semgrep's scanned-file list cannot be matched and the check ends `incomplete` (safe direction, misleading text "e.g. too large").
- One scan at a time; analyzer limits (1.5 GiB, 2 CPUs, 256 pids) are fixed defaults. Docker-only boundary; a second backend is deferred.
- Cleanup (5D): the engine runner cancels cleanly (SIGINT to the process group, SIGKILL after a grace period), the sandbox client is always killed if still running, and the reaper keeps going when Docker hangs. A descendant that changed directory can outlive a killed worker (its container still has the container-side deadline).

## Secrets scan (`hardcoded-secrets`, Stage 11)
A separate check, `saferun/engine/secretscan.py`, running **gitleaks 8.30.1** (`gitleaks dir`, MIT) in the verified analyzer container (no network, read-only project, same limits, no host fallback). Chosen by the owner over detect-secrets (noisier, thinner vendor coverage), custom Semgrep rules (output carries the matched line) and trufflehog (verifies secrets online by default, AGPL-3.0, larger). The binary is pinned by the SHA-256 of its release archive; the baked config `rules/gitleaks.toml` and the tool version are image labels compared before every use, so an older analyzer image fails verification until `saferun init`.
**Untrusted input.** `--config` points only at the baked file; `--ignore-gitleaks-allow` is set; `.gitleaksignore` files are deleted from the private copy; the environment is not forwarded. Output is parsed strictly (a JSON list of objects with a rule id; anything else is `error`), capped (100 000 read, 1 000 kept), de-duplicated, `clean_text`-sanitized; paths must be relative inside the copy. Files over `--max-target-megabytes` are skipped silently by gitleaks, so SafeRun finds them itself and reports `incomplete`.
**Values never leave the container.** `--redact`; the parser takes only `RuleID`, `File`, `StartLine`, `EndLine`; `Secret`, `Match`, `Fingerprint` are discarded; the message is fixed text; stderr of a failed run is not echoed. Tests feed a sentinel in `Secret`/`Match`/stderr and assert it appears nowhere (finding, JSON, text report, CLI output).
**Verdict.** Every finding is HIGH (FAIL). `--no-secrets-check` → `skipped` (at best WARNING); missing image → `unavailable`; mismatching labels → `error`; files over 1 MB → `incomplete`. It is on by default, so `saferun run` also performs it; analyzer images built before gitleaks report `error` until `saferun init`.
**Limits.** Known vendor token formats only; the generic entropy rule is disabled (high false-positive rate), so plain passwords and unrecognised tokens are missed; example keys in docs/tests can be flagged; nothing is verified as live; binary files and git history are not scanned; vendored folders (incl. `node_modules`) are skipped like in the Semgrep check. Files matching SafeRun's own credential signatures are withheld at copy time (`workspace-sensitive-files`) and never reach gitleaks. Image size 709 MB → 770 MB (gitleaks binary 21.96 MB; rest not investigated).

## Package-name check (`saferun check-names`)
A separate command (`saferun/pkgnames.py`); `scan` and `run` do not call it. It reads declared Python dependency names (`requirements*.txt`, `pyproject.toml` directly in the given directory, plus names on the command line), normalises them (PEP 503) and compares them with `saferun/data/top_pypi.txt` (snapshot of the 10 000 most downloaded PyPI names, hugovk's top-pypi-packages dataset, date in the header; regenerated with `tools/update_top_pypi.py`). A name outside the snapshot within 1 edit (2 when both have 8+ characters) of a snapshot name is "similar"; names of 4 characters or fewer are never matched or used as a target. Similarity uses a delete-neighbourhood index then a real optimal-string-alignment check (tested against brute force). Offline by default. `--online` (explicit) asks `https://pypi.org/simple/<name>/` whether a name outside the snapshot exists and its first upload (8 parallel lookups, 15 s timeout, 32 MB cap, 2 000 names per run, names only); every failure is "could not check", exit 2, never a pass. Untrusted-project reading: only files directly in the directory; symlinks and files over 1 MB are not read; nothing executed or installed.
**Limits.** Heuristic: on the dataset itself ~98% of single-edit typos of popular names are caught and ~7% of real packages just below the cutoff are falsely flagged (distance 2 from length 8 adds ~3 points of false alarms); look-alikes of packages outside the snapshot, prefix/suffix tricks and non-PyPI ecosystems are not covered; the snapshot ages; download counts are not looked up (PyPI's API has none). Details: [docs/cli.md](docs/cli.md).

## Setup workflow (`saferun init`, `saferun status`)
`saferun/setup.py` only orchestrates existing verification (pinned-digest image check, analyzer lock/labels/rules hash, OSV manifest validation) and adds no trust of its own. Components: `python` image, `analyzer` (Semgrep, OSV-Scanner, gitleaks, rules; not separable), `osv-db`. A component is *ready* only if verification passes at that moment; valid ones are skipped without a network probe; everything installed is re-verified, failure is reported, never assumed. Actions: `docker pull <repo>@<pinned digest>` for Python; the published analyzer `analyzer-v1.2.0` is installed by digest after a cosign check (needs cosign and internet: ghcr.io, TUF, Rekor; no unsigned install, no silent fallback) or built with `init --build-local` (`docker/analyzer/build.sh`, needs a checkout); `osvdb.update` for OSV data (atomic, keeps old data on failure). Rebuilding/repairing an analyzer that failed verification needs `--repair` or an interactive confirmation. Offline: nothing downloaded, valid components still used, missing ones listed with preload instructions, exit 1. A scan with an unready component adds `setup: … -> fix: saferun init --only X` on stderr only. ## Dependency findings: fix label and accepted risks (Stage 10)
A dependency finding carries `fix_kind` (`patch`/`minor`/`major`), computed in `saferun/engine/osv.py` (`fix_kind`, `version_key`) from the installed version and the nearest fixed release above it, using only data OSV supplies; shown next to "fixed in" and in the Upgrade plan. `saferun/engine/accept.py` and `saferun scan --accept-file FILE`: `[[accept]]` entries (`id` or alias, optional `package`, required `reason` and `expires`) move matching dependency findings out of the verdict into a visible **Accepted risks** list; expired entries apply no more (a current entry wins over an expired one for the same finding).
**Decisions (owner).** The accept file is read **only** from `--accept-file`, never from the scanned project (an in-project `.saferun-accept.toml` is ignored with a stderr note); a bad file is exit 64 before any scan. Accepted findings stay visible but leave FAIL/WARNING; accepted findings are removed *before* `compute_verdict`, so verdict rules are untouched. A check whose findings are all accepted becomes `passed`; incomplete/error statuses never change.
**Unchanged.** `schema_version` 1; new keys are additive (`fix_kind` when known; `accepted`/`accept_notes` only with an accept file). **Limits.** Label by version numbers only (`0.x` minors are often breaking; non-numeric versions get no label); only dependency findings can be accepted; dates use the local calendar date of the scanning machine.

## Plain-English findings (Stage 12)
A finding can carry `explanation` (one or two short sentences: what it is, why it matters, how to fix it) next to the unchanged `message`. The text report prints `In plain words: …` under the message (default on, no flag; styled report wraps it); JSON has the key only when one exists. Texts live in `saferun/engine/explain.py` (tested table keyed by rule id; Semgrep ids match exactly or from `saferun.python.` on; a template for dependency findings uses `fix_kind` and the nearest fixed release, naming no version when only commit hashes exist; one generic text for `secrets.*`; withheld files; syntax). Covered: all 14 Semgrep rules, withheld-file rules, syntax findings, secrets, dependency findings; unknown ids have none. The engine fills `explanation` after the checks (before accepted findings are split out), so hand-built findings (the website fixture) have none and serialise as before. Every text is under 300 characters (the text report's one-line limit).
**Decisions (owner).** One line per finding, no table; wording uses "can"/"could", never claims an attack will happen or a fix guarantees safety; texts are not in the rules file or the image, so no analyzer release is needed. **Limits.** General guidance, not advice for a specific code base; the dependency text does not describe the particular vulnerability.
